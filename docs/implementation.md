## 2. 구조 — 코어 하나, 입구 두 개

```text
config/ktb13.yaml     팀 설정: 소스 레포, ref, 포함·제외 경로, 결정 로그 연도
src/tka/
  ingest/             가져오기 → 파일 고르기 → 정규화 → 청킹
  decisions/          결정 로그 → 결정 표 (+ supersedes 보정 파일)
  index/              키워드 인덱스, 벡터 인덱스
  retrieve/           하이브리드 검색 + RRF
  answer/             프롬프트, 인용 검증
  core.py             search_docs(), get_decision()  ← 근거 찾기·글 만들기
  service.py          최신 main 따라가기 + 도구 호출 + 호출 로그  ← 입구가 같이 쓴다
  calllog.py          호출 로그 쓰기·읽기 (data/calls.jsonl)
  cli.py              tka 명령: ask · search · decision · log  (얇은 껍데기)
  mcp_server.py       MCP 도구: get_decision · search_docs  (얇은 껍데기)
eval/
  golden.yaml              골든셋 (검사·확인 시트: src/tka/golden.py)
  drift_cases.yaml         모순 정답셋 후보
  run_eval.py              recall@5, 인용 정확도 채점
  results/                 실행마다 소스 커밋·설정 해시와 함께 저장
```

- **CLI와 MCP에는 로직을 두지 않는다.** 그래야 v1에서 MCP를 "감싸기만" 할 수 있다(D14). 둘 다 `service.KnowledgeService`를 부르고, 도구 본문은 한 줄이다.
- 사용자 명령은 `tka` 하나다(8단계). 개발·평가 명령(`ingest`, `decisions check`, `retrieve eval`, `answer eval`, `golden`, `evaluation`, `baseline`)은 기준 커밋으로 도는 `python -m tka.<모듈>`로 따로 둔다. 같은 일을 하는 명령을 두 곳에 두지 않는다.
- 위 폴더 이름은 예시다. 원칙만 지키면 바꿔도 된다.

### 테이블

| 테이블 | 칸 | 비고 |
|---|---|---|
| `documents` | 레포, 경로, 커밋, 제목(frontmatter `wiki`), 문서 유형(`type`), `updated` | frontmatter `status`는 작성 상태라 결정 판단에 쓰지 않는다 |
| `chunks` | 문서, 헤딩 경로, 본문, 문서 상단 콜아웃, **시작·끝 줄 번호** | 줄 번호가 있어야 `경로:줄` 인용이 된다 |
| `decisions` | 날짜, 파트, 결정 내용, 영향 파트, 상세 링크(해석된 경로), 번복 여부 | v0 |
| `facts` | 주제 키, 값, 출처 청크, 추출 방식(규칙·LLM), 날짜 | v1 (D10·D11) |

## 3. 단계별 방법

### ① 가져오기·고르기

- 소스 레포는 **별도 캐시 폴더에 clone**해서 쓴다. 작업 중인 로컬 폴더를 직접 읽지 않는다.
  - 실제 사례: 2026-09-28 로컬 wiki 폴더는 `docs/fs-1-4-conversion` 브랜치에 있었다. 모르고 읽으면 main에 없는 문서가 섞인다.
- 설정에 **소스별 ref**를 둔다. 평가할 때는 브랜치 이름이 아니라 **고정 커밋**을 적는다. 소스가 하루에도 여러 번 바뀌어서, 커밋을 고정하지 않으면 봇·베이스라인·골든셋이 서로 다른 문서로 채점된다.
- 파일 목록 = `git ls-files` 결과 + 포함·제외 규칙(context.md §3).
- **소스 문서를 이 레포에 복사하지 않는다.** 이미 5벌이다. 6번째 사본을 만들지 않는다.
- **완료 기준**: 뽑힌 파일 목록이 context.md §3 규칙과 개수까지 일치한다.

### ② 청킹 — 가장 공들일 곳

- **마크다운 파서**(markdown-it-py 등)로 읽는다. 정규식은 코드 블록 안의 `#`을 헤딩으로 착각한다.
- **`<details>` 블록을 청크 단위로 다룬다.** FS-2 엔드포인트 40개, FS-1 테이블 28개가 전부 `<details><summary>` 안에 있다. 헤딩 기준으로만 자르면 "### 주문 · 5개" 아래 API 5개가 한 덩어리가 된다. `<summary>`를 그 청크의 제목으로 쓴다.
- **첫 H2 앞의 인용 블록(`>`)은 문서 콜아웃**으로 보고 그 문서의 모든 청크에 붙인다. AI-5 13행의 `book_passage` 폐기 안내가 여기 해당한다.
- 표의 **행 중간**은 자르지 않는다. 한 청크 상한(`MAX_CHARS`, 지금 1500자)을 넘는 긴 표만 행 사이에서 나누고 나뉜 조각마다 머리행을 다시 붙인다. FS-4 정책 체크리스트(126행, 1.1만 자)가 한 청크면 e5가 앞 512토큰만 보고 나머지를 버린다. 목록도 항목 사이에서만 나눈다. 코드 블록은 나누지 않는다.
- 긴 구역은 굵은 라벨 문단(`**입력**`, `**출력 (200)**`)에서 먼저 나누고 라벨을 제목 경로에 붙인다. AI-1 ③처럼 `<details>` 하나가 240줄인 경우다.
- 구역의 첫 청크는 헤딩·`<details>` 줄부터 시작한다. 인용 범위에 제목이 들어가고 골든셋 근거(헤딩부터 적은 것)가 한 청크 안에 들어간다.
- `MAX_CHARS`는 **900자**다(6단계 측정). 1500자면 청크의 16%가 e5의 512토큰을 넘어 뒤가 잘렸다(한국어 글자당 0.5토큰). 900자로 줄이자 RRF recall@5가 89% → 94%(16 → 17/18)가 됐다.
- frontmatter는 파싱해 `documents`에 넣고 본문 청크에서는 뺀다.
- NBSP·NFC 정규화는 **줄 안에서만** 한다. 줄이 합쳐지면 줄 번호가 어긋난다.
- git이 한글 경로를 8진수로 출력하므로 `core.quotepath=false` 또는 `-z` 출력을 쓴다.
- **완료 기준**: 청크를 JSONL로 덤프해 눈으로 확인한다. 특히 ① AI-5 콜아웃이 모든 청크에 붙었는지 ② FS-2가 엔드포인트별로 나뉘었는지 ③ 표가 잘리지 않았는지.

### ③ 결정 표

- 결정 로그(`docs/dec/000-decision-log.md`)는 `| 날짜 | 파트 | 결정 | 영향 파트 | 상세 |` 표다. 마크다운 파서로 읽는다. `4f6a6a6` 기준 17행, 상세 링크 15개(링크 없는 칸 2개). 구현: `src/tka/decisions/table.py`, 검사: `python -m tka.decisions check`.
- GFM 표는 모자란 칸을 빈 칸으로 채우므로 칸 수 대신 빈 칸(파트·결정)을 문제로 본다. 파서가 한글 링크를 `%EC…`로 바꾸므로 되돌려 비교한다.
- 날짜에 **연도가 없다**(`09-21`). 연도는 설정값으로 붙인다.
- 상세 링크는 상대 경로다(`../ai/...`, `../../.agents/...`). 레포 루트 기준 경로로 바꿔 저장한다. "클라우드 확인 대기"처럼 링크가 없는 행도 있다.
- **"번복" 관계는 표에 칸이 없다.** 문구("번복" 등)로 일부만 잡히므로 보정 파일 `config/ktb13-supersedes.yaml`을 둔다. wiki 레포가 `_preserve-overrides.tsv`로 예외를 관리하는 방식과 같다. 행은 날짜 + 결정 글에 든 말로 찾고, 딱 한 행이 맞아야 한다. 적는 것: 뒤집은 이전 결정(`replaces`), 옛 서술이 남은 곳(`old_text_at`, D15 ①), 로그 안에서 대체한 행(`superseded_by`).
- **이슈 번호로 되돌림을 자동으로 잇는다**: "AI #246 되돌림"처럼 이슈 번호 바로 뒤에 되돌림·번복·철회가 오면, 같은 이슈 번호를 적은 이전 행을 대체됨으로 표시한다. 2026-09-30 실제 사례(09-30 행이 09-28 행을 되돌림)로 만들었다. 보정 파일은 커밋 하나에 묶이지만 이 규칙은 어느 커밋에서나 맞다. 대체된 결정은 get_decision에서 기본으로 빼고(D17), 대체한 결정 밑에 "대체한 이전 결정"으로 보여 준다(`include_superseded`로 따로 볼 수 있다).
- context.md §5의 뒤집힌 결정 7개 중 결정 로그에 행이 있는 것은 3개(09-21 LangChain, 09-24 BM25, 09-15 book_passage)다. ④ feed GET(09-16), 임베딩 e5(09-16), 추천 이유 엔드포인트(09-08), DB 분리(09-08~09)는 로그에 없어서 `get_decision`이 모른다. D16(결정 누락 잡기)의 실제 사례다.
- **완료 기준**: 결정 표 행 수 = 로그 행 수. 링크가 모두 실제 파일로 해석된다.

### ④ 검색

- 순서: 키워드 인덱스 → recall@5 / 벡터 인덱스 → recall@5 / RRF 결합 → recall@5. **세 숫자를 표로 남긴다.**
- **트라이그램 함정**: 3글자 미만 검색어는 매칭되지 않는다(SQLite FTS5 문서에 명시). "배송", "결제", "쿠폰" 같은 두 글자 단어가 흔하다. 트라이그램만 쓰면 이런 질문이 빠진다 → Kiwi와 비교하거나 짧은 검색어만 따로 처리한다.
- **e5 함정**: 질의에는 `query: `, 문서에는 `passage: ` 접두어를 붙여야 한다(모델 카드에 명시). 빼먹으면 조용히 품질이 떨어진다.
- 서비스 ① 검색은 "키워드 3 : 벡터 1 가중 RRF"를 쓴다(결정 로그 09-23). 가중치를 줄지는 골든셋으로 비교한다. AI 레포 `app/search/`와 `tests/test_search_rrf.py`가 참고가 된다.
- **완료 기준**: recall@5 표(키워드 / 벡터 / RRF)가 `eval/results/`에 커밋·설정 해시와 함께 있다.
- **결과 (2026-09-30, `eval/results/2026-09-30-retrieval/`)**: 가장 좋은 방식은 **RRF 3:1 · Kiwi · 청크 900자 · 결정 행 단위, recall@5 94%(17/18)**, 근거 전부 56%(10/18). 서비스와 같은 키워드 3 : 벡터 1이다.
  - 벡터만 72%(13/18), Kiwi 키워드만 83%(15/18). 합치면 오른다.
  - **제목 경로·문서 안내를 붙이는 게 효과가 있다**: 본문만 색인하면 벡터 61%, RRF 72%로 떨어진다(각각 −2, −3문항).
  - **결정 로그는 행 하나를 검색 단위로 넣는다**: 로그가 여러 행씩 한 청크면 결정 한 행이 묻힌다. 행 단위로 바꾸자 근거 전부가 44% → 56%(8 → 10/18)가 됐다(결정 로그 + 명세를 함께 적은 문항이 많다).
  - 놓친 문항은 g19(취향 벡터 없는 개인화) 하나다. 답변에서는 결정 표 찾기(별칭·조사 처리)가 따로 잡아 넣는다(⑤).
  - 별칭(`config`의 `aliases`)을 검색어에 붙여 봤지만 recall은 같고 근거 전부가 10 → 9로 줄어 기본으로 끈다.
  - 튜닝용 20문항으로 고른 값이라 과적합일 수 있다. 채점용 질문으로 다시 잰다.

### ⑤ 답변과 인용 검증

- LLM에게 **문장마다 근거 청크 ID를 붙인 구조화 출력(JSON)**을 받는다.
- **코드로 검증**한다: 청크 ID가 실제 검색된 목록 안에 있는가. 없으면 그 문장을 빼거나 "근거 없음"으로 표시한다.
- 인용 문자열(`레포/경로:줄@커밋`)은 **LLM이 쓰지 않고, 청크 메타데이터로 코드가 렌더링**한다. 없는 경로를 지어내는 일이 원천적으로 없어진다.
- **결정 우선 규칙**: 질문과 관련된 결정이 결정 표에 있으면 컨텍스트에 함께 넣고, "결정 로그가 문서 본문보다 우선, 답은 지금 값으로 한다"를 지시한다.
- **이력은 세 경우에만 한 줄** (plan.md D15): ① 옛 내용이 문서·코드에 아직 남아 있을 때 ② 질문이 옛 값을 전제할 때 ③ "왜?"를 물을 때. ①은 LLM에 맡기지 않고 코드로 판단할 수 있다 — 검색된 청크 중 결정 상태가 폐기·대체됨인 것이 있으면 이력 한 줄을 붙이게 한다.
- 근거가 부족하면 "모름"으로 답하게 하고, 골든셋의 "모름이 정답" 문항으로 확인한다.
- **완료 기준**: 골든셋 전 문항에서 인용 검증을 통과하지 못한 문장이 답에 남지 않는다.
- **구현 (`src/tka/answer/`, 2026-09-30)**: `uv run tka ask "질문"`, 채점용은 `python -m tka.answer eval --model <모델>`.
  - 근거는 두 가지다. 결정 `[D…]`: 결정 표 찾기 3개 + 검색에 걸린 결정 행. 문서 `[C…]`: 검색 상위 5개 조각(제목 경로·문서 안내 포함). 검색이 놓친 g19를 결정 표 찾기가 잡는다.
  - LLM은 `{unknown, sentences: [{text, sources}]}`만 JSON 스키마(strict)로 돌려준다. 넘기지 않은 근거 ID는 지우고, 근거가 하나도 안 남은 문장은 뺀다.
  - 이력 ①(옛 서술이 남은 곳)은 코드가 판단한다: 조각에 보정 파일의 `old_text_at` 줄이 있으면 `[주의] N행은 옛 서술이다. 지금 결정: …`을 붙여 넘긴다.
  - 재시도는 SDK의 연결 오류·429·5xx만(2번). 400·401·402·403·404는 다시 불러도 같으므로 평가를 그 자리에서 멈추고 그때까지의 답을 남긴다(gpt-6-luna가 모든 문항에서 404였다).
- **결과**: 20문항 전부에서 뺀 문장 0개, 인용 정확도 100%(38/38). 정답률은 ⑥.

### ⑥ 평가

- 20문항이면 **처음엔 사람이 직접 채점**한다. 익숙해지면 LLM 채점을 추가한다(우아한형제들도 이 순서).
- 지표: 정답률, 인용 정확도(⑤의 검증으로 자동), 검색 관련성, 답변 충실성, 답변 관련성.
- 함정 문항은 **지금 값을 맞혔는지**로 채점한다. 이력을 말했는지는 점수에 넣지 않는다. "왜?" 문항은 이력 자체가 답이다.
- 베이스라인(Claude Code 새 세션)의 답도 같은 질문 형식·같은 기준으로 `eval/results/`에 기록한다 (`tka.baseline`, `tka.evaluation`). 새 세션은 사용자 설정(`~/.claude`)을 읽지 않는다(`--setting-sources project,local`). 사용자 CLAUDE.md의 "tka 도구로 확인한다" 줄이 섞이는 것을 2026-10-06에 확인했다.
- 골든셋 20문항은 **튜닝용**이다. 최종 비교는 따로 모은 **채점용** 질문으로 한다(plan.md §4-1). 채점용은 튜닝 중에 열지 않는다.
- **자동 생성 검증셋** (plan.md D18, `tka.bigset`): 다른 계열 LLM(`openai/gpt-4o-mini`)이 기준 커밋 문서에서 `eval/bigset.yaml`을 만든다. 문항 id는 `b001`부터, 유형별로 dev·test 반씩.
  - 구절은 봇의 청크와 상관없이 문서 크기에 비례해 30줄 창을 무작위로 뽑는다. 청크 경계에 맞춰 뽑으면 검색이 실제보다 좋아 보인다. 보정 파일의 옛 서술 줄이 든 창은 뺀다.
  - 근거 줄은 코드가 검사한다(창 안, 비어 있지 않음, 10줄 이하). 모름 문항은 "답이 있다면 나올 단어"가 문서 전체에 없을 때만 남긴다.
  - 레포 주인은 `tka.bigset review`가 뽑은 무작위 20문항만 확인한다.
  - 2026-10-06 생성 결과: 139문항(dev 71 · test 68, 비용 약 $0.03). **모름 문항 0개** — 4o-mini는 지시문을 고쳐도 문서에 있는 주제만 물었고, 코드 검사가 모두 걸렀다. 표본에 약한 문항이 섞여 있다(예: "왜?"를 묻는데 정답에 이유가 없음, 문서끼리 다른 값 중 한쪽만 정답). 레포 주인 표본 확인 전이다.
- **LLM 채점** (`tka.judge`): 사람 채점과 같은 기준(정답 1 · 부분 0.5 · 오답 0)으로 `scores-llm.yaml`을 만든다. 사람 채점 파일은 덮어쓰지 않는다. 문항 자체가 틀렸으면 `item_problem`으로 표시해 정답률에서 뺀다. 틀린 답 유형은 코드가 정한다.
  - 믿을 만한지(골든셋 20문항 두 실행에서 사람 채점과 비교):

    | 채점 모델 | 사람과 일치 | 봇 vs 베이스라인 |
    |---|---|---|
    | 사람 | — | 90% vs 92.5% |
    | `openai/gpt-6.1-sol` (2026-09-30) | 37/40 | 사람과 같은 순서 |
    | `openai/gpt-4o-mini` (2026-10-06) | 31/40 | 85% vs 82.5%, **순서가 뒤집힌다** |

    4o-mini는 사람이 정답으로 본 답을 부분으로 깎는 쪽으로 어긋나고(9건 중 7건), 길게 답하는 베이스라인을 더 깎는다. 그래서 **봇·베이스라인 실행과 채점은 보류**했다(실험 비용 한도 $3 안에서 다시 정한다).
- 결과마다 **소스 커밋과 설정 해시**를 함께 저장한다. 그래야 나중에 수치를 비교할 수 있다.
- **결과 (2026-09-30, 튜닝용, `eval/results/2026-09-30-bot-vs-baseline.md`)**: 봇 90%(18/20), 베이스라인 92%(18.5/20). 봇은 함정 4/4(베이스라인 3.5/4)와 문서끼리 다름 g16에서 이기고, g06(이유 하나 빠뜨림)·g15(FS-1이 검색 안 됨)·g21(범위 밖 `backup/`에만 있는 결정)에서 졌다. 질문당 $0.0009·1.3초로 베이스라인($0.127·21.5초)보다 100배 넘게 싸고 16배 빠르다.

### ⑧ MCP (D14, D17)

- `core.py`의 `get_decision`, `search_docs`를 MCP 도구로 감싼다(`src/tka/mcp_server.py`, MCP SDK 2.x의 `MCPServer`). stdio 방식으로 본인 Claude Code에 user 범위로 등록한다:
  `claude mcp add --scope user tka -- uv run --directory <이 레포> python -m tka.mcp_server`
- **실제 사용은 최신 main을 따른다.** 평가는 기준 커밋으로 고정하지만 코딩 중에는 신선도가 더 중요하다(plan.md §6). 부를 때 10분이 지났으면 `git ls-remote`로 main을 확인하고, 바뀌었으면 `.cache/live/`에 받아 다시 만든다. 확인에 실패하면 마지막 커밋 기준으로 답하고 그 사실을 알린다. `--pinned`면 기준 커밋 그대로다. `tka` 명령도 같다(`src/tka/service.py`).
- **도구는 답이 아니라 근거를 돌려준다**(D17): 조각 원문, 결정 상태, `레포/경로:줄@커밋` 인용, 인덱스 기준 커밋. 답 문장은 부르는 쪽이 쓴다.
- **연결 시점은 도구별**(D14): `get_decision`은 결정 표가 로그와 맞으면 바로(5번 PR), `search_docs`는 recall@5가 기준을 넘으면(6번 PR).
- **`search_docs`** (2026-09-30 연결): 6단계 기본 방식(RRF 3:1 · Kiwi · 청크 900자)으로 찾아 조각 원문·제목 경로·문서 안내·`레포/경로:줄@커밋`을 돌려준다. 조각에 보정 파일의 옛 서술 줄이 있으면 `[주의]`로 지금 결정을 붙인다(조각 전체가 폐기된 건 아니라 빼지 않는다). 색인은 결정 표와 같은 커밋 사본으로 처음 검색할 때 만들고, 새 main이면 다시 만든다. 임베딩은 캐시돼 바뀐 청크만 계산한다. 처음 검색 7.8초(모델을 먼저 로컬에서 불러온다), 이후 즉시.
- 도구 함수는 MCP 서버의 다른 스레드에서 불린다. sqlite3 연결은 만든 스레드에서만 쓸 수 있어 임베딩 캐시는 쓸 때마다 짧게 연다(처음 연결 때 실제로 깨졌다).
- **호출 로그** (8단계): MCP 도구와 `tka` 명령을 부를 때마다 `data/calls.jsonl`에 한 줄 남긴다(시각, 입구 `mcp`·`cli`, 도구, 인자, 기준 커밋, 돌려준 근거 위치, 걸린 시간. `ask`는 모름 여부·답·비용도). 로그를 못 남겨도 답은 돌려준다. 평가 실행은 남기지 않는다. `tka log`로 보고, `--empty`면 결과 없음·모름만 본다(문서 빈 곳 후보). 틀린 답은 골든셋에 추가한다.
- MCP는 live 작업 폴더에서 돌므로 로그도 거기 쌓인다. `tka`도 같은 폴더에서 부르면(README의 alias) 로그가 한 파일에 모인다.
- 2026-09-30 확인: MCP 서버는 연결돼 있었지만 호출 로그가 한 줄도 없었다(연결 뒤 실제로 불린 적이 없다). plan.md §1-1대로 `~/.claude/CLAUDE.md`에 언제 부를지 한 줄 적는다.
- 도구 설명(description)이 호출 여부를 좌우한다. "팀 결정·명세·정책을 확인해야 할 때"처럼 **언제 불러야 하는지**를 쓴다.

## 4. 구현 순서 — 한 줄이 PR 하나

순서는 plan.md D9(평가 먼저)를 따른다. 골든셋과 베이스라인은 코드가 필요 없고, 베이스라인 점수가 먼저 있어야 이후 PR의 개선을 수치로 말할 수 있다.

| # | PR | 확인 방법 |
|---|---|---|
| 0 | 프로젝트 기본 설정: uv, `.gitignore`, 설정 파일(기준 커밋 포함), README | `pytest`·`ruff` 통과, `.env`가 git에 안 잡힘 |
| 1 | 골든셋 `eval/golden.yaml` 20문항(튜닝용). Claude가 기준 커밋으로 근거 줄을 맞추고, **정답은 레포 주인이 확인한다** | `python -m tka.golden check` 문제 0건 |
| 2 | 베이스라인 채점 (Claude Code 새 세션) | `eval/results/`에 정답률·인용 정확도 |
| 3 | 가져오기·고르기 → 파일 목록 출력 | 기준 커밋에서 34개 (context.md §3) |
| 4 | 정규화 + 청킹 → 청크 덤프 | AI-5 콜아웃, FS-2 엔드포인트 분리, 표 보존 |
| 5 | 결정 표 파서 (+ 보정 파일) → `get_decision` MCP 연결 | 행 수·링크 해석, `claude mcp list` |
| 6 | 키워드 / 벡터 / RRF + recall@5 → 기준을 넘으면 `search_docs` MCP 연결 | 세 숫자 표 |
| 7 | 답변 생성(CLI·채점용) + 인용 검증 + 채점 | 베이스라인과 비교 표. 최종 비교는 채점용 질문으로 |

PR마다 이슈 → `feature|fix|chore|hotfix/<이슈번호>-<이름>` 브랜치 → PR로 올리고, 병합은 레포 주인이 한다.
