# 설계와 로드맵

> 2026-09-28 작성. 본문은 지금 기준만 적는다. 설계 결정이나 로드맵을 뒤집을 때만 §10 "바뀐 결정"에 한 줄 남긴다.

## 1. 목표

- 팀원이 "이거 어디 있어 / 왜 이렇게 정했어 / 지금 뭐가 맞아"를 레포와 위키를 뒤지지 않고, **근거 링크와 함께** 답받는다.
- 문서와 코드가 어긋난 곳을 사람이 발견하기 전에 드러낸다.
- 포트폴리오: 베이스라인 대비 **질문 유형별** 성능을 수치로 보여준다. 증명 방법은 §4-1.
- **차별점** (2026-09-28, §9 조사 반영): 코드·문서 Q&A는 기존 제품(Unblocked, Sourcegraph, DeepWiki 등)이 이미 잘한다. 이 프로젝트는 ① **결정이 뒤집힌 이력을 구분해서 "지금 기준"으로 답하는 것**, ② **문서끼리 모순된 곳을 찾는 것**, ③ **결정 로그에 안 남은 결정을 잡아 로그를 채우는 것**(D16)에 집중한다. ②는 제품이 거의 없고 연구 단계인 영역이다. ②가 어긋난 뒤에 찾는다면 ③은 어긋나기 전에 잡는다.

## 1-1. 개발 중 활용 시나리오 (2026-09-28)

한마디로 **Claude Code 옆에 팀 문서를 다 읽은 동료를 붙여두는 것**이다. 평소처럼 Claude Code에 일을 시키면, Claude Code가 모르는 팀 정보(다른 레포의 명세, 다른 파트의 결정)가 필요할 때 봇에게 묻는다. 봇을 따로 열 필요가 없다.

예시 작업: **"BE가 AI 챗봇(③)을 연동한다."** 아래 대화는 설명을 위한 예시이고, 인용한 결정·날짜는 결정 로그 기준이다. 이 작업은 실제로 2026-09-28 BE `f32eb67`에서 시작됐다(context.md §4). 연동 코드와 FS-2 명세가 벌써 어긋나 있다(context.md §5-1 #2).

**① 작업 시작 전 — 흩어진 맥락을 한 번에 모은다**
> BE 개발자: "AI 챗봇 연동 시작하는데 알아야 할 거 다 모아줘"
> 봇: ③ 명세(요청·응답 필드, 에러 코드) · 관련 결정(긴 이유 `reason_long`은 BE가 저장 — 09-15, 취향 벡터 없어도 구매 이력으로 개인화 — 09-28) · ⚠️ 응답 형식이 문서마다 다름(결정 로그 `{message, data}` vs FS-2 `{result, data, error}`) · ⚠️ FE→BE 챗봇 API가 FS-2에 아직 없음

지금은 문서 9개와 결정 로그를 직접 뒤져야 하고, ⚠️ 같은 함정은 대부분 놓친다.

**② 코딩 중 — AI 코딩 도구에 팀 기억을 연결한다 (가장 많이 쓰일 곳)**

Claude Code·Cursor는 지금 열린 레포만 본다. BE 레포에서 작업하는 도구는 wiki 결정이나 AI 명세를 몰라 옛 설계대로 짜거나 필드명을 추측한다. 봇을 MCP로 연결하면 도구가 코딩 중에 스스로 묻는다. 봇은 답 문장이 아니라 근거를 돌려주고, 답은 Claude Code가 쓴다(D17).
> Claude Code → 봇: "④ feed 호출 메서드가 뭐야?"
> 봇: `[현행] ④ feed 메서드는 GET — 결정 로그 09-16 (AI)` · 근거 `KTB4-13th-wiki/docs/ai/1-model-api/spec.md:<줄>@<커밋>` · 기준 wiki main `<커밋>`

이력(09-16에 POST에서 바뀜)은 붙이지 않는다. 질문이 옛 값을 전제하거나 옛 내용이 문서·코드에 남아 있을 때만 붙인다(D15).

연결 방법:
- **user 범위로 등록한다**(`claude mcp add --scope user ...`). 소스 레포 파일을 건드리지 않고 5개 레포 어디서든 쓴다.
- **`~/.claude/CLAUDE.md`에 한 줄을 넣는다.** 예: "KTB4-13th 레포에서 다른 파트 API, 명세 필드, 팀 결정을 추측하지 말고 봇 도구로 확인한다." 도구 설명만으로는 Claude Code가 잘 부르지 않는다.
- 도구는 만들어지는 대로 하나씩 붙인다(D14). 결정 표가 생기면 `get_decision`, 검색 기준을 넘으면 `search_docs`.

**③ PR 올리기 전 — 명세·결정과 어긋난 곳을 미리 잡는다**
> 작성자: "이 PR, 명세나 결정이랑 안 맞는 거 있어?"
> Claude Code가 diff를 읽고 봇에게 ③ 명세를 물은 뒤: "응답에 `reason` 필드가 있는데 명세는 `reason_short`다. `reason`은 폐기된 이름이다."

리뷰어가 한 명뿐이라 리뷰에서 놓치기 쉬운 것을 올리기 전에 거른다. 작업 중인 diff는 Claude Code가 이미 읽으므로 봇에는 명세·결정만 있으면 된다. 그래서 v2 코드 도구를 기다리지 않는다.

**④ 리뷰할 때 — 결정을 바꾸는 변경을 알아챈다**
> 리뷰어: "이 PR이 기존 결정을 바꾸는 거야?"
> Claude Code가 PR 브랜치의 diff를 읽고 봇에게 결정을 물은 뒤: "그렇다. 09-24 결정은 '검색에 BM25를 쓰지 않는다'인데 이 PR이 BM25를 다시 넣는다. 결정 로그에 새 줄이 필요하다."

코드는 바뀌었는데 결정 로그에 남지 않는 일(응답 형식 불일치의 원인)을 막는다.

**⑤ 매주 — 어긋남 리포트**

Discord에 올린다. 항목마다 초안이 붙고, 올릴지는 사람이 정한다.
- 문서끼리·문서와 코드가 안 맞는 곳 N건
- 결정인데 결정 로그에 없는 것 N건과 로그 한 줄 초안(D16)
- 봇이 "모름"으로 답한 질문 = 문서가 비어 있는 곳

| 언제 | 누가 | 어디서 | 얻는 것 | 필요한 단계 |
|---|---|---|---|---|
| 작업 시작 전 | 개발자 | Claude Code (MCP), CLI | 흩어진 명세·결정·함정 한 번에 | 결정: 결정 표 이후 / 명세: 검색 이후 / ⚠️ 모순 경고: v1 |
| 코딩 중 | **AI 코딩 도구** | MCP | 팀 결정에 맞는 코드 | 본인만: 도구별로 단계적 (D14), 팀 배포: v3 |
| PR 전 | 작성자 | Claude Code (MCP) | 명세·결정 위반 사전 발견 | v1 (diff는 Claude Code가 읽는다) |
| 리뷰 | 리뷰어 | Claude Code (MCP) | 결정 변경 여부 확인 | v1 |
| 매주 | 팀 전체 | Discord | 어긋남 목록, 결정 누락 초안, 문서 빈 곳 | v1 리포트, 이슈 초안은 v3 |

**봇 없이 오늘 시작하는 법**
1. wiki를 **별도 폴더에 main 기준으로 clone**한다. 작업용 로컬 wiki 폴더는 다른 브랜치에 있을 수 있다.
2. 작업 레포의 Claude Code에 `/add-dir`로 그 폴더를 붙인다.
3. 개발하면서 팀 결정·명세를 물은 질문과 Claude Code가 틀린 답을 기록한다.

이건 베이스라인 ①(wiki를 연 Claude Code)을 실제 개발에서 매일 쓰는 것과 같다. 기록은 봇이 이겨야 할 목록이자 골든셋 재료가 된다. 채점용으로 쓸 질문은 기록할 때 따로 떼어 두고 튜닝 중에 열지 않는다(§4-1).

**필요 없는 때**: 레포 하나 안에서 끝나는 질문("이 함수 어디서 불러?")은 Claude Code만으로 충분하다. 이 봇은 질문이 **레포 경계, 문서 경계, 시간(결정 이력)을 넘을 때** 값을 한다. 파트별로 레포가 나뉜 이 팀은 BE↔AI 연동을 시작하는 시점부터 그런 질문이 가장 많아진다.

**지금은 하지 않는 것**
- 다른 팀도 쓰는 플랫폼(B안). 전환 조건은 §8에 있다.
- 코드 수정, PR 작성, 코멘트 같은 쓰기 행동.
- 코드 전체 임베딩.

## 2. 설계 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | **코드는 임베딩하지 않고 도구(grep, 파일 읽기, 심볼 목록, git log)로 탐색한다** | 코드 질문은 식별자를 정확히 맞춰야 하는데 임베딩은 여기에 약하다. 코드는 PR마다 바뀌어 인덱스가 금방 낡는다. 레포 전체가 수만~10만 줄 규모라 탐색으로 충분하다 |
| D2 | 문서는 **키워드 검색 + 벡터 검색을 RRF로 합친다** | 결정·명세 문서는 자연어라 의미 검색이 먹히고, 엔드포인트명·테이블명은 키워드가 이긴다 |
| D3 | **레포 간 계약 인덱스**(FE 호출 → BE 매핑 → AI 라우터 → 명세)는 LLM 없이 파싱으로 만든다 | 결정적으로 풀 수 있는 건 결정적으로 푼다. 업계도 API 명세 대조는 AI 없이 규칙 도구(oasdiff 등)로 한다. 여러 레포를 잇는 것 자체는 Sourcegraph Deep Search·Unblocked도 하므로 차별점이 아니다(차별점은 §1) |
| D4 | 청크마다 **결정 상태(현행·폐기·대체됨)**를 붙인다 | 이 팀은 결정이 자주 뒤집혔다(context.md §5). 상태가 없으면 폐기된 결정을 사실처럼 답한다 |
| D5 | 모든 주장에 **`레포/경로:줄@커밋` 인용**을 강제하고, 근거가 없으면 "모름"이라고 답한다 | 검증할 수 없는 답은 팀에서 신뢰받지 못한다 |
| D6 | **읽기 전용**으로 시작한다 | 쓰기 도구는 사람 승인 흐름과 함께 나중에 붙인다 |
| D7 | **A안: 우리 팀용**으로 시작하되, **팀 하나 = 설정 파일 하나**로 만든다 | 레포 목록, 포함·제외 경로, 계약 파일 위치를 코드에 박지 않아야 나중에 다른 팀으로 넓힐 수 있다 |
| D8 | 서비스 레포가 아닌 **새 레포, 개인 계정** | 배포·의존성·CI 분리, 서비스 리뷰 큐 오염 방지, 봇이 자기 코드를 검색하는 문제 회피. 조직은 private 생성 불가이고, 과정이 끝난 뒤에도 포트폴리오로 남겨야 한다 |
| D9 | **평가를 먼저 만든다**: 골든셋 → 베이스라인 → 검색 → 답변 순서 | 기준 없이 만들면 "느려짐 → 고침"만 반복하게 되고 결과를 설명할 수 없다 |
| D10 | 지식을 **세 가지 형태**로 저장한다: ① 문서 조각(검색용) ② 결정 표(결정 로그 파싱) ③ 사실 표(문서에서 뽑은 "주제 · 값 · 출처") | 질문 답변은 ①, "지금 뭐가 맞아"는 ②, 모순 찾기는 ③으로 푼다. 셋 다 같은 원본에서 만든다 (2026-09-28) |
| D11 | 모순 찾기는 **뽑기는 규칙 + LLM, 비교는 규칙, 판정은 사람** | 표로 된 사실(엔드포인트, 컬럼, 응답 형식)은 파싱으로 뽑고 서술형 사실만 LLM으로 뽑는다. 같은 주제에 값이 다른 것은 규칙으로 찾는다. LLM도 문서 불일치를 절반 남짓밖에 못 찾는다는 결과(§9)가 있어 LLM 단독 판정에 기대지 않는다. 의도된 차이인지는 사람이 판정한다 (2026-09-28) |
| D12 | 베이스라인을 **두 개** 둔다: Claude Code(도구 탐색), DeepWiki(public 레포 무료 Q&A) | "기존 도구 대비 어디서 나은가"를 수치로 보여준다. 13기 레포는 모두 public이라 DeepWiki를 쓸 수 있다 (2026-09-28) |
| D13 | **문서 모순 찾기를 코드 조사보다 먼저** 만든다 | 코드 Q&A는 기존 제품이 잘하는 영역이라 차별점이 약하다. 문서 모순 찾기는 정답셋(context.md §5-1 7건)도 이미 있다 (2026-09-28) |
| D14 | **MCP를 쪼개서 앞당긴다**: 본인 PC의 본인 Claude Code에 도구가 만들어지는 대로 하나씩 연결하고, 팀원 전체 배포는 v3. 연결 조건은 도구에 LLM이 끼는지로 나눈다. ① 규칙으로 만드는 `get_decision`: 결정 표가 로그와 행 수가 같고 링크가 모두 해석되면 바로. ② 검색만 하는 `search_docs`: recall@5가 로드맵 5단계에서 정한 기준 이상이면. ③ LLM이 만든 내용이 섞이는 도구(v1 모순 경고 등): 정답셋으로 정밀도를 확인한 뒤 | **앞당기는 이유**: ① 실제로 쓰이는 입구가 MCP다 — CLI는 사람이 일부러 열어야 하지만 MCP는 AI 코딩 도구가 알아서 부른다(§1-1). ② 추가 비용이 작다 — `core.py` 함수를 도구 정의로 감싸기만 한다. ③ 실제 개발 중 질문이 로그로 쌓여 골든셋 확장 재료와 사용 기록이 된다. ④ BE↔AI 연동 시기에 레포를 넘는 질문이 가장 많다. **쪼개는 이유**: ① LLM이 지어낸 내용을 AI 도구가 그대로 믿고 코드에 반영할 수 있다. 규칙으로 만든 근거와 원문 조각에는 이 위험이 없고, 근거를 읽고 판단하는 건 부르는 쪽이다(D17). ② 팀 배포는 인덱스 동기화·호스팅 부담이 있다. **기존 결정과의 관계**: 서비스(AI-6)는 소비자가 BE 하나라 MCP 전송을 쓰지 않았고, 그때 정한 전환 조건 중 하나가 "다중 소비자"였다. 이 봇은 여러 AI 도구와 팀원이 부르므로 그 조건에 해당한다 (2026-09-28) |
| D15 | 답은 **지금 값만** 기본으로 한다. 바뀐 이력은 ① 옛 내용이 문서·코드에 아직 남아 있을 때 ② 질문이 옛 값을 전제할 때 ③ "왜?"를 물을 때만 한 줄 붙인다. 이력 추적(결정 표, D4)은 봇 안에서 계속한다 | 묻는 사람 대부분은 지금 값만 필요하다. 이력을 늘 붙이면 답이 길어지고, MCP로 부르는 AI 도구에도 잡음이 된다. 반대로 ①②에서 한 줄이 없으면 옛 문서를 본 사람이 "봇이 틀렸나"로 헷갈리거나 틀린 전제로 코드를 짠다. 이력을 보여줄지와 별개로, 추적하지 않으면 폐기된 값을 지금 값처럼 답한다 (2026-09-28) |
| D16 | **결정 누락 잡기**: 결정이 난 곳(회의 안건 이슈, 머지된 PR)을 읽어 "결정인데 로그에 없다"를 잡고, 결정 로그 형식(`\| 날짜 \| 파트 \| 결정 \| 영향 파트 \| 상세 \|`) 한 줄 초안을 만든다. 후보 고르기는 규칙(닫힌 회의 안건 이슈, 명세·컨트롤러·마이그레이션·`ai.yml`을 건드린 PR), 결정인지 판단과 초안은 LLM, 기존 결정과 대조(번복·신규·이미 있음)는 규칙. 초안은 주간 리포트에 싣고 올리는 건 사람이다. v1은 회의 안건 이슈, v3에서 머지 PR로 넓힌다 | 봇은 결정 표로 "지금 값"을 답하는데(D4, D15), 로그에 안 올라간 결정이 있으면 옛 값을 확신하며 답한다. 문서 모순의 상당수도 여기서 나온다(context.md §5-1 #1: 응답 형식이 바뀌었는데 로그에 기록이 없다). 모순 찾기는 어긋난 뒤에 찾고, 이건 어긋나기 전에 잡는다. 과거 이력(결정 로그 행이 추가된 날, 회의 이슈)으로 기다리지 않고 채점할 수 있다. 회의 안건 이슈는 public이고 개수가 정해져 있어 v1 범위로 맞다 (2026-09-28) |
| D17 | **MCP 도구는 답이 아니라 근거를 돌려준다**: 조각 원문, 결정 상태(현행·폐기·대체됨), `레포/경로:줄@커밋` 인용, 인덱스 기준 커밋. 폐기·대체된 조각은 기본으로 빼고 이력을 요청할 때만 넣는다. `get_decision` 결과에는 "결정 로그 기준"임을 밝힌다. 답 문장은 부르는 쪽(Claude Code)이 쓴다. 봇의 답변 생성(로드맵 6단계)은 CLI와 채점에 쓴다 | 부르는 쪽이 이미 LLM이라 봇이 답을 한 번 더 만들 필요가 없다. 봇은 Claude Code가 혼자 못 하는 것만 한다: 다른 레포의 문서 찾기, 결정 상태 붙이기, 같은 문서 5벌 중 원본 고르기. 답변 생성이 코딩용 경로에서 빠져 더 일찍 쓸 수 있고, 봇이 지어낸 문장이 코드에 들어갈 일이 없다. 폐기 조각을 기본으로 빼는 것은 D15와 같은 이유다 (2026-09-28) |

## 3. 구조

```text
[입구]  CLI (v0) → MCP 본인만 (도구별 단계적, D14) → MCP 팀 배포 (v3) → (선택) Slack/Discord 봇
        주간 리포트: 모순 · 결정 누락 초안 · 문서 빈 곳 (v1)
                              │
[두뇌]  CLI: 질문 해석 → 도구 선택 → 근거 수집 → 인용 달린 답변
        MCP: 근거만 돌려주고 답은 부르는 쪽이 쓴다 (D17)
        도구: search_docs · get_decision · find_facts · (v2) grep_code · read_file · list_endpoints
                              │
[저장]  ① 문서 조각 인덱스   ② 결정 표          ③ 사실 표            (v2) 계약 표
        키워드+벡터(RRF)     날짜·결정·번복관계   주제·값·출처·날짜     명세 vs 코드 엔드포인트
                              │
[수집]  설정 파일(대상 레포·경로) → git ls-files → 정규화(NBSP·NFC) → 헤딩 단위 청킹
        + 결정 로그 표 파싱 + 사실 추출(표는 파싱, 서술은 LLM)
        main에 push되면 바뀐 파일만 다시 처리 (v3)
```

기능과 저장소의 대응:

| 기능 | 쓰는 저장소·도구 | LLM의 역할 |
|---|---|---|
| 물어보면 답하기 | ① 문서 조각 | 찾은 조각으로 답 작성, 인용 |
| "왜? 지금 뭐가 맞아?" | ② 결정 표 → 상세 문서 ① | 지금 결정으로 답한다. "왜?"면 이전 → 현재를 요약한다 (D15) |
| 문서끼리 모순 찾기 | ③ 사실 표 (같은 주제·다른 값) | 서술형 사실 추출, 모순 설명 초안 |
| 결정 누락 잡기 (v1, D16) | 회의 안건 이슈(v1)·머지 PR(v3) + ② 결정 표 | 결정인지 판단, 로그 한 줄 초안 (올리는 건 사람) |
| 구현됐는지 확인 (v2) | 계약 표 + 코드 도구 | 필요할 때 코드 읽고 설명 |
| 명세 변경 영향 (v2) | 계약 표 | 바뀐 명세를 부르는 다른 레포 코드 설명 |
| 고칠 거리 초안 (v3) | 모순 리포트 항목 | 이슈·문서 수정안 초안 (올리는 건 사람) |

MCP로 부를 때는 "LLM의 역할" 칸의 답 작성을 부르는 쪽(Claude Code)이 한다(D17).

## 4-1. 증명 방법 — 포트폴리오 (2026-09-28)

"사내 문서 RAG 챗봇"은 포트폴리오에 흔하다. 보여줄 것은 문제가 진짜였다는 것, 왜 그렇게 풀었는지, 어떻게 증명했는지다. 만드는 동안 증명이 쌓이게 한다.

**README 첫 화면 표** — 이 표를 채우는 방향으로 만든다.

| 주장 | 숫자 | 비교 대상 | 단계 |
|---|---|---|---|
| 뒤집힌 결정을 지금 기준으로 답한다 | 함정 문항 정답 수 | Claude Code, DeepWiki | v0 |
| 근거 없이 답하지 않는다 | 인용 정확도, "모름" 문항 정답 수 | Claude Code, DeepWiki | v0 |
| 문서 모순을 찾는다 | 7건 중 찾은 수(재현율), 리포트 중 진짜 문제 비율(정밀도) | LLM에 문서를 통째로 주고 찾게 한 것 | v1 |
| 결정 누락을 먼저 잡는다 | 과거 결정 중 잡은 수, 평균 며칠 먼저 | 결정 로그에 실제로 추가된 날 | v1 |
| 팀이 실제로 썼다 | MCP 호출 수, 봇 리포트를 보고 팀이 고친 PR 수 | — | v1~ |

마지막 줄이 가장 강하다. "만들었다"와 "팀이 썼고 이걸 고쳤다"는 급이 다르다.

**만들 때 지킬 것**
- **설계 결정마다 끄고 켜서 비교한다.** "왜 그렇게 했어?"에 숫자로 답한다.

  | 설계 결정 | 끄면 떨어질 것으로 예상하는 곳 |
  |---|---|
  | 문서 상단 콜아웃을 모든 청크에 붙임 | 함정 문항 (AI-5 `book_passage`) |
  | 결정 표를 문서 본문보다 우선 | 함정 문항 전체 |
  | 트라이그램 vs Kiwi | 두 글자 단어 문항 ("배송", "결제") |
  | 인용 문자열을 코드가 만듦 | 지어낸 경로 수 |
  | 모순 찾기: 규칙+LLM vs LLM 단독 | 재현율·정밀도 |

- **튜닝용과 채점용 질문을 나눈다.** 같은 문항으로 튜닝하고 채점하면 시험지를 보고 공부한 셈이다. 채점용은 팀원이 쓴 질문(답을 아는 사람이 만든 질문이라는 의심도 없앤다)이나 따로 떼어 둔 개발 중 기록 질문, v1 이후 MCP 로그의 질문으로 만든다.
- **PR마다 전후 수치를 PR 본문에 적는다.** PR 템플릿에 칸을 둔다. git 이력이 곧 "어떤 변경으로 몇 문제 더 맞혔나"의 기록이 된다.
- **틀린 답을 유형별로 모은다**: 검색 실패 / 검색은 맞았는데 답이 틀림 / 폐기된 문서를 인용. 무엇을 고쳤더니 어떤 유형이 줄었는지 남긴다.
- **비율과 개수를 같이 쓴다.** 20문항이면 한 문제가 5%p다. "85%"만 쓰지 않고 "17/20"을 함께 쓴다.
- **질문당 비용과 응답 시간을 기록한다.**
- **실제 사례는 생긴 순간 캡처한다.** 봇이 팀 작업 중 모순을 잡은 순간, 팀원이 그걸 보고 고친 PR 링크. 레포가 매일 바뀌어 나중에 재현할 수 없다.

**결과물**
- README 순서: 한 줄 소개 → 실제 사례 하나(context.md §5-1 #1 응답 형식) → 30초 데모 → 결과 표 → 구조 그림 → 설계 결정과 끄고 켠 비교 → 한계 → 재현 방법.
- 데모: 베이스라인이 **실제로 틀린** 함정 문항으로 Claude Code 단독과 봇 연결을 나란히 보여준다.
- 재현: 소스 레포 5개가 public이라 누구나 명령 하나로 같은 채점을 돌릴 수 있다. 채점할 때 소스 커밋을 고정한다.
- 글 한 편: 문제 → 조사(§9) → 바꾼 결정(§10) → 결과 → 한계.
- 모순 정답셋과 결과 공개: 팀 동의 후.

## 6. 함정

- **같은 문서 5벌**: 원본 하나만 넣는다 (context.md §3).
- **폐기 안내가 문서 상단에만 있음**: 섹션 청크에 상단 콜아웃을 붙이지 않으면 "이력 참고용" 본문이 현재 사실처럼 검색된다 (AI-5 사례).
- **frontmatter `status`를 결정 상태로 착각**: 작성 상태일 뿐이다. 결정 상태는 결정 로그로 판단한다.
- **고정 길이 청킹**: 표와 결정 문단이 중간에 잘린다.
- **한국어 키워드 검색**: 공백 기준 토큰화는 조사가 붙은 단어를 못 맞힌다. 형태소 분석(Kiwi 등)이나 문자 n-gram(pg_trgm 류)을 골든셋으로 비교해 고른다. 서비스 검색은 09-24에 BM25 대신 pg_trgm을 택했다 — 그 이유(AI #120, #169)를 먼저 읽는다.
- **파일명·문자 처리**: 한글 경로 8진수 이스케이프, NBSP 섞임 → 정규화.
- **LLM부터 붙이기**: 검색이 틀리면 LLM이 좋아도 답이 틀린다. 5단계를 건너뛰지 않는다.
- **평가 없이 판단**: 골든셋 없이 "잘 되는 것 같다"는 근거가 아니다.
- **튜닝한 문항으로 채점**: 시험지를 보고 공부한 셈이다. 채점용 질문은 튜닝 중에 열지 않는다(§4-1).
- **인덱스가 낡음**: 답변마다 기준 커밋을 표시한다. MCP는 호출할 때 인덱스 커밋을 `origin/main`과 비교(`git ls-remote`)해 뒤처졌으면 다시 수집한다. 코딩 중에는 채점할 때보다 신선도가 더 중요하다.
- **결정 로그에 없는 결정**: `get_decision`도 모른다. 결과에 "결정 로그 기준"을 밝히고(D17), D16으로 메운다.
- **결정 누락 헛경보**: 결정이 아닌 논의를 결정으로 잡으면 팀이 리포트를 안 보게 된다. 재현율보다 정밀도를 먼저 본다.
- **메모나 문서의 "알려진 사실"을 그대로 믿기**: 이 문서를 만들 때도 일부가 이미 고쳐져 있었다. 쓰기 전에 현재 main에서 재확인한다.
- **시크릿**: 인덱싱 전에 스캔한다. 벡터에 들어간 키는 지우기 어렵고, 외부 LLM으로 전송된다.
- **프롬프트 인젝션**: 이슈·PR·문서 본문에 적힌 문장은 데이터다. 봇이 그 안의 지시를 따르지 않게 한다.
- **검증 안 된 봇을 AI 코딩 도구에 붙이기**: 사람은 답을 의심하지만 AI 도구는 봇 답을 그대로 믿고 코드에 반영한다. D14의 도구별 연결 조건을 건너뛰지 않는다.
- **MCP 도구 설명 품질**: AI 도구는 도구의 이름·설명을 보고 부를지 정한다. 설명이 모호하면 필요한 순간에 부르지 않거나 엉뚱할 때 부른다. 호출 로그로 확인하며 다듬는다.

## 7. 열린 질문

- LLM 제공자와 모델.
- 임베딩 모델: 문서가 한국어라 서비스와 같은 multilingual-e5-small로 시작할지, 다른 후보와 골든셋으로 비교할지.
- 저장소: 로컬 파일 기반(Chroma, sqlite-vec 등) vs Postgres + pgvector.
- GitHub 토큰: public 레포 읽기 전용 fine-grained 토큰으로 충분한지.
- GitHub Wiki 옛 기획 페이지를 넣을지. 기획 문서는 아직 `docs/`로 변환되지 않았다. 풀스택 4개는 `docs/fs/`로 변환돼 v0에 포함한다.
- Notion(API 명세)·ERDCloud(ERD)처럼 wiki 밖에 있는 원본을 소스로 넣을지.
- 외부 LLM으로 팀 문서를 보내는 것에 대한 팀 합의. 레포가 public이라 유출 위험은 낮다.
- 채점용 질문을 팀원에게 받을 수 있는지(몇 개, 언제).
- `search_docs` MCP 연결 기준으로 삼을 recall@5 값. 로드맵 5단계에서 베이스라인 결과를 보고 정한다.
